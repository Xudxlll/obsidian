## 规划节点：自然语言怎样变成步骤

plan_node 从 messages 最后一条取用户问题，附上三个工具的名称与说明，请模型按编号输出。程序按换行拆开，再只保留首字符为数字的行。最终 plan 是字符串列表，不是经过严格 Schema 验证的任务对象。

如果模型用了项目符号、汉字编号或前导解释，解析可能丢掉步骤。更稳妥的教学改进是明确 step_id、tool、arguments、success_condition，但这里仍保留原文，不将改进冒充原实现。

## bind_tools：让模型知道可调用什么

`llm.bind_tools(FINANCE_TOOLS)` 将工具定义交给模型接口。它不意味着工具已经执行，也不会在绑定时下载股票数据。执行阶段得到 response.tool_calls 后，程序才遍历名称与参数，找到相应函数。

一个 tool_call 含名称、参数以及关联 ID。ToolMessage 使用这个 ID 回传结果，让模型体系能把结果与具体请求对应起来。它与普通“我查到了……”的 assistant 文字不同。

## 执行节点：索引推进与证据积累

execute_node 取当前 plan[step_index]。如果包含“结论”或“综合”，它跳过工具并递增位置；否则组织本步提示词，只允许相应工具，调用绑定工具后的模型，再执行每个返回的 tool_call。

本步结果加入 tool_result，新响应与 ToolMessage 加入 messages，最后 step_index 加 1。路由只检查是否达到计划长度，不检查工具是否成功，也不检查本步是否得到必要字段。

因此会出现一种重要情形：工具没有真正调用、返回 None 或失败文本，但步骤索引照样推进。这是“控制流程完成”与“研究任务成功”的区别。

## 汇总节点：真正看到了哪些资料

summarize_node 从 messages 第一条取原始需求，把全部 tool_result 拼起来，要求结构化分析。它没有再次读取数据库，也没有自动补上计划中遗漏的数据。

原课堂测试问题只问“实时股价”，汇总提示词却固定要求“综合投资价值判断”。这会扩大任务范围。合理应用应让输出深度匹配用户需求：只问报价就返回报价与时点，不必把每次查询扩成投资评价。

## compile 与 invoke 各做什么

builder.add_node 注册函数，add_edge 与 add_conditional_edges 定义走向，compile 生成可执行图，invoke 给图输入状态。图并不是由模型随机画出来的，而是开发者预先定义；模型在节点内部完成规划与工具选择。

## 三个离线演练

**空计划**：把 plan 设为空，追踪下一次 plan[0] 为什么失败。你不需要请求模型就能看出缺少校验。

**工具失败**：假设行情函数返回 None，跟踪 tool_result 怎样把它变成字符串，再看总结节点是否仍会执行。然后设计一个 status 字段表示失败。

**两条同类步骤**：计划分别查甲乙公司，手工追踪 step_index=0、1、2，确认没有重复或跳过，消息里的股票代码没有混用。

> [!question]- 为什么日志应同时记录 step_index、工具名和参数？
> 步骤号能说明进度，工具名说明动作，参数说明动作针对谁。只记录“完成第二步”，无法判断是否查询了正确公司与日期。
