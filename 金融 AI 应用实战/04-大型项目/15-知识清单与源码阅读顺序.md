## 你不需要同时学完所有框架

这套应用可以按依赖顺序拆成五组知识。先理解每组解决的问题，再深入 API。下面不是说你必须记住所有类名，而是让你知道代码出问题时该查哪一层。

| 知识 | 要回答的问题 | 项目中的落点 |
| --- | --- | --- |
| Python 函数、列表、字典、异常 | 输入怎样变成输出 | 所有节点与工具 |
| async/await、gather、Semaphore | 怎样等待多个角色并控制并发 | pipeline |
| 消息、提示词、Token、工具协议 | 模型这次看到什么、能要求什么 | runner 与 core.types |
| 状态、阶段、轮次、合并 | 证据和决策怎样沿流程传递 | state 与 pipeline |
| 财务、行情、时点与数据质量 | 资料能否支持金融结论 | DataInterface 与数据工具 |
| 角色配置与结构化输出 | 如何复用岗位并提供可显示字段 | YAML 与 summary_agent |
| 数据库、队列与事件 | 长任务如何保存和展示 | analysis_service、QueueService |
| Embedding 与检索记忆 | 怎样带入相关历史经验 | FinancialSituationMemory |
| 测试、权限与部署 | 怎样证明应用可用并可控 | 验收、Nginx 与 Docker 配置 |

## 推荐你实际打开源码的顺序

1. pipeline.py：只看 run_pipeline 的阶段顺序，先不要钻进所有 helper。
2. state.py：对照每个阶段读写字段。
3. orchestrator/agents.py：看分析师如何取数据、调用模型与返回报告。
4. researcher_factory、research_manager、trader：理解研究意见与计划的区别。
5. debator_factory、risk_manager：理解风险讨论围绕什么。
6. summary_agent 与 runtime：追踪展示字段和最终决策来自哪里。
7. runner 与 providers：理解一次调用怎样经过统一接口与恢复逻辑。
8. analysis_service 与 Reader：连接用户任务和数据来源。

每次阅读只追踪一个字段，例如 trader_investment_plan，从生产者一路找到消费者。这样比按文件名从 A 读到 Z 更容易形成系统理解。

## 几项没有证据不能宣称的能力

没有在当前可读分析链里看到训练循环，就不能说这个项目训练了金融大模型。角色提示词不是模型微调；Chroma 不是自动学习收益规律；“量化专家”角色不是已验证量化策略；生成价格与评级不是交易成交。

同样，读取源码说明静态理解，实际部署和业务效果需要另行验证。本教程的证据索引把可读源码与封装文件分开，防止把文件存在当作功能已证明。

> 文档可能概括旧设计，源码也可能有缺失。当前执行链、配置、可读性和实际运行结果决定能确认到哪一步；它们不一致时应明确写出。
