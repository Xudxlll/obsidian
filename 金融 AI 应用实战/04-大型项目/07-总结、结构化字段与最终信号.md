## 为什么写完报告还要做结构化总结

页面上的价格卡片、风险等级与摘要，需要程序容易读取的字段。summary_agent 把报告转成 JSON，包括 key_indicators、model_confidence、risk_assessment、analysis_summary、investment_recommendation、analysis_reference 和 final_signal。

文字到 JSON 的转换仍由模型完成，之后 json.loads 只能验证基本 JSON 语法。当前补齐必需键的逻辑不等于完整校验类型、范围、引用真实性或金融逻辑。

## 总结实际上只读了截断后的材料

_build_user_message 对交易计划、最终决定、基础报告和辩论历史分别设置字符截断长度；其他报告每项只取前 300 字。这控制上下文成本，但可能删掉后面的条件、反例和数据缺失说明。

摘要看起来清楚，不等于读过全文。若关键风险在被截掉的部分，汇总输出可能过度乐观，验收应包含“关键限制是否仍保留”。

## 固定字段名可能与动态角色不一致

总结固定读取 market_report、news_report、fundamentals_report、sentiment_report。分析师报告却按 internal_key 动态命名。若配置中实际生成 financial_news_report 或 social_media_report，它们可能走 other_reports，而不是固定主输入。

因此应检查配置 slug、internal_key、report_key 和总结消费者四者是否对应。界面都显示“新闻分析”，不代表后台键名相同。

## 失败默认值不能当成真实低风险

全部有效输入不足时存在失败结构；JSON 解析失败或普通异常也有兜底字段，其中有 Hold、confidence=50 或风险 Low 等值。这些是程序默认值，不是对标的作出的真实风险判断。

一个安全的展示需要把生成状态与业务值分开：先显示是否成功，再显示评级。不能让失败默认值在界面上看起来像正常“低风险、持有”。

## structured_summary 与 Runtime decision 是两份产物

Runtime 在流水线之后还会选择一段 final_signal 文本再 process_signal。优先顺序是 final_trade_decision → investment_plan → 风险 judge_decision → trader_investment_plan。这里的 investment_plan 来自研究主管。

因此开启研究、关闭风险时，后处理可能优先读取研究主管裁决，而不是交易员计划。不要以为页面所有卡片都天然来自同一份最终报告；需要追踪每个字段的生产者和消费者。

> [!question]- model_confidence=80 是否就是 80% 胜率？
> 不能这样理解。除非有明确校准方法与样本外验证，它只是生成或解析出的字段。模型自报信心、系统状态与统计概率是不同概念。
