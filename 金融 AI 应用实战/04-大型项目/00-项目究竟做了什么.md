> [!abstract] 先用一句业务语言理解
> 这是一套把股票数据、多个模型角色、研究讨论和报告展示连接起来的应用。它试图模拟“收集材料—各专业研究—多空讨论—形成计划—风险审阅—交付报告”的过程。

## 用户要解决什么问题

金融人员提供标的、分析日期与角色配置，希望得到一组分工报告和综合结果，而不是只收到模型随口回答的一段话。系统还要管理任务身份、执行进度、模型连接与数据来源。

它主要处理研究材料与分析文字。“交易员”“最终交易信号”是项目中的角色和输出字段名称；可读的交易员节点生成计划文本，没有在该节点调用券商下单工具。不能把一份计划报告当作真实成交记录。

## 输入、处理、输出分别是什么

| 层次 | 具体内容 |
| --- | --- |
| 输入 | 股票身份、分析日期、选中的分析师与模型/阶段配置 |
| 外部材料 | 行情、财务、新闻等数据能力，以及可选历史记忆 |
| 处理中间物 | 分析师报告、多空观点、主管裁决、交易计划、风险讨论 |
| 输出 | 报告集合、结构化总结、决策文字提取结果、耗时与错误记录 |

这里的“信号”是模型输出经后处理得到的结构，不是经过回测证明的超额收益信号。model_confidence 也不是天然经过校准的胜率。

## 它用了什么知识

你已在小案例中见过的 Prompt、工具、状态、角色与报告交接继续存在。大型项目新增统一模型接口、异步并发、可配置角色、数据读取层、任务与用户身份、事件、记忆、错误恢复和应用部署。这些是应用工程知识，不是从零预训练大模型。

## 必须先知道的材料边界

项目共有 556 个 .py 文件：450 个可作为 UTF-8 文本读取，106 个以 ENCZ1 开头、不能作为普通 Python 正文阅读。前端目录只有 dist 构建产物，没有提供 Vue 源组件。教程对可读核心流程作源码拆解，对封装路由与 Worker 标为未核实，不伪造它们的内部步骤。

README 将引擎称为 LangGraph；当前可读核心实际通过 asyncio 和手写状态合并调度。AnalysisRuntime 的旧别名包含 Graph，不等于创建了 LangGraph StateGraph。应以当前 pipeline.py 为准。

## 你最后应该能向别人讲出来

“它帮研究人员组织取证和分工分析；外面是任务与报告应用，里面是多阶段异步流水线；模型通过工具读数据并产生文本，后续角色读取上游产物；是否可靠要另外检验数据、论证与任务状态，不能由角色名或报告格式推断。”

> [!question]- 这个大型项目与课堂 LangGraph 小例子最大的区别是什么？
> 小例子确实注册 StateGraph 节点和边；大型项目当前通过 Python 异步函数直接调度。两者都能表达工作流，但不是同一套具体实现。
