## 简介

这期视频的主线，是把 Skill、MCP、RAG、Agent、function calling、workflow、sub-agent 这些容易被营销包装成“新物种”的概念，重新拆回到大模型应用里最朴素的几件事：

- 大模型本身只是根据上下文继续生成文本。
- 所谓对话、记忆、联网、检索、工具调用，本质上都是在想办法把合适的信息放进上下文，或者让程序代替人完成确定性的操作。
- Agent 不是神秘的新智能，而是夹在用户、大模型、工具之间的调度程序：它把自然语言需求拆成步骤，把模型输出转成工具调用，再把工具结果塞回上下文。
- MCP 和 function calling 都是“约定”，但约定的位置不同：function calling 约束模型如何向 agent 表达工具调用意图，MCP 约束 agent 如何发现和调用外部工具服务。
- Skill 更像一种带说明文档和脚本目录的任务包，它把一部分流程经验固化下来，让 agent 在执行任务前按需读取规则和工具。

作者的核心判断是：这些概念不是彼此完全并列的技术革命，而是大模型产品发展中的不同层次。越靠程序和固定流程，越稳定但越不灵活；越靠纯 agent 自主决策，越灵活但越不可控。未来真正会胜出的方向，可能不是某个术语本身，而是把 MCP、Skill、workflow、模型配置等复杂内容隐藏起来，让普通人直接用得起来的产品形态。

## 总结（按时间顺序）

### 00:00 - 01:00 先把所有概念放回大模型起点

视频开头先强调：现在 AI 圈里的词很多，看起来复杂，但都可以从最基础的大语言模型出发理解。

大模型最底层的能力并不是“会做事”，而是根据输入预测下一个词。模型变大以后表现出了更强的语言理解和生成能力，于是被称为大语言模型，也就是 LLM。直接让 LLM 做文字接龙并不够像智能应用，所以人们把输入组织成一问一答的形式，让它表现为“对话”。

这里的关键起点是：模型本身还是一次输入、一次输出。它没有天然的持续记忆，也不会自己联网、操作文件或调用工具。后面所有概念，基本都是围绕“如何包装这一次输入输出”展开。

### 01:00 - 02:25 Prompt、Context、Memory：都是在组织输入

作者把用户比作老板，把 LLM 比作只能一问一答的员工。每次给模型的话，被称为 prompt。

prompt 里面又可以拆出不同部分：

- `context`：背景信息、参考资料、历史对话等上下文。
- `instruction`：这一次真正要模型完成的指令。
- `memory`：把历史对话或历史总结重新塞进 context，让模型看起来像“记得”之前发生过什么。

所谓记忆并不是模型真的在脑子里永久记住了东西，而是系统在每次请求前，把过去的信息重新整理、压缩、放回上下文。记忆压缩也是再次调用模型做摘要，以减少上下文长度。

这一段的重点是：对话、上下文、记忆，本质上都是 prompt 工程的一部分，都是在管理“这次让模型看见什么”。

### 02:26 - 04:14 Search 和 RAG：给模型补充参数以外的信息

接着作者指出，模型靠训练参数回答问题，容易不知道最新信息，也容易胡说。解决方法不是让模型真的自己上网，而是让外部程序帮助它获取资料，再把资料放进上下文。

最简单的扩展是联网搜索：

- 模型判断自己需要资料。
- agent 或外部程序执行搜索。
- 搜索结果被整理后放回 context。
- 模型基于这些资料继续生成答案。

如果检索对象不是互联网，而是本地文档、数据库或知识库，就会引出 RAG。RAG 的核心流程是把文档切片、向量化，用语义相似度找出相关片段，再把片段放入上下文增强生成。

所以 Search 和 RAG 在抽象层面很像：==它们都是获取模型参数以外的信息，并把信息加入上下文。区别只是信息来源、检索方式和工程实现不同。==

### 04:21 - 05:55 Agent、function calling、MCP：三者分别站在不同位置

当用户不想手动搜索、复制资料、再喂给模型时，就会写一个程序代理人来做这些事。这个程序夹在用户和模型之间，负责判断什么时候调用工具、怎么把工具结果交回模型，于是被称为 agent。

这里作者把 agent 讲成一个“传话筒”和“调度器”：

- 用户把任务交给 agent。
- agent 把任务和上下文交给模型。
- 模型按约定格式表达是否要调用工具。
- agent 解析模型输出，去调用工具。
- 工具结果再被塞回上下文，让模型生成最终回答。

function calling 解决的是 agent 和模型之间的格式约定。因为模型默认输出自然语言，程序不好稳定解析，所以需要让模型用 JSON 等固定结构表达“我要调用哪个函数、传什么参数”。

MCP 解决的是 agent 和外部工具服务之间的调用约定。工具不一定都写在 agent 主程序里，也可以拆成独立服务。那 agent 就需要知道如何列出工具、如何调用工具、如何接收返回值。MCP 就是这一层协议。

一句话区分：

- function calling：模型对 agent 说“我想调用什么工具”的格式约定。
- MCP：agent 对工具服务说“我要怎么发现和调用你”的协议约定。
- Agent：夹在用户、模型、工具之间负责调度的程序。

### 05:55 - 07:29 Workflow 和 LangChain：把稳定流程固定下来

作者接着讨论 agent 的交互形态：它可以是 CLI、IDE、桌面助手，也可以是更通用的聊天式产品。

但纯 agent 有一个问题：如果任务流程很稳定，每次都让它重新规划，会浪费 token，也会不稳定。比如“提取英文 PDF、翻译成中文、保存为 Markdown”这个任务，里面的 PDF 提取和保存文件完全可以写成固定脚本，中间翻译再交给模型。

这就引出两类更固定的流程工具：

- LangChain：用编程方式把多个步骤串起来。
- Workflow：用低代码或拖拽方式把多个步骤串起来。

它们的共同点是：把任务流程提前设计好，而不是每次都让 agent 自由发挥。这样更稳定、更省 token，但灵活性会下降。

### 07:31 - 08:53 Skill：把说明文档和脚本打包给 agent 读取

当输入格式、输出格式和任务分支变多时，单独写一个 workflow 可能会爆炸，因为你无法为所有排列组合都单独做一套流程。

作者提出的 Skill 思路是：

- 准备一个目录。
- 把常用脚本、工具、模板放进去。
- 写一个 `SKILL.md` 之类的说明文件。
- 让 agent 在执行相关任务前读取这个说明，再按任务需要调用目录里的脚本。

所以 Skill 不是一个神秘的新能力，它更像是“给 agent 的任务说明书加工具包”。它比纯 workflow 更灵活，因为具体流程可以由 agent 根据任务判断；它又比纯 agent 更可控，因为关键规则和可用脚本已经被提前整理好了。

作者调侃 Skill 像是把 prompt 换了个地方存起来，但它确实提供了一个实用的中间形态：把经验固化成文档和脚本，让 agent 按需加载。

### 08:53 - 09:15 Sub-agent：本质是上下文隔离

复杂任务会让主 agent 的上下文越来越长，也会让任务过程混乱。于是出现 sub-agent。

作者认为 sub-agent 的本质并不复杂：它就是把某些独立子任务交给单独的上下文去完成，避免子任务过程中的大量细节污染主上下文。

主 agent 只需要拿到子任务结果，不必保留子 agent 的全部中间思考和历史记录。

所以 sub-agent 的核心价值是上下文隔离，而不是凭空多出一种新的智能。

### 09:36 - 10:41 两个容易混淆的问题：function calling vs MCP，Skill vs MCP

作者专门澄清了两个常见误区。

第一，function calling 和 MCP 不是同一层东西。

function calling 是模型和 agent 之间的格式约定，让模型用程序能解析的形式表达工具调用意图。MCP 是 agent 和工具服务之间的协议，约定工具列表、调用方法、参数和返回值。

所以 MCP 不能“取代”function calling，因为它们不在同一个连接点上。

第二，Skill 和 MCP 也不是同一层东西。

Skill 是给 agent 读取的说明文档和资源目录，可以包含脚本、模板、使用规则。MCP 是工具服务协议。Skill 可以把一些工具脚本直接放在目录里，让 agent 按说明调用；但这不代表 Skill 和 MCP 是完全同类的东西。

从实用角度看，常用工具未来可能会内置进 agent 主程序，或者被基础 Skill 包吸收，因此 MCP 对普通用户可能会越来越隐形。

### 10:42 - 12:20 从刚性到柔性：LangChain、Workflow、Skill、纯 Agent 的区别

作者把这些形态放在一条轴上看：从刚性到柔性，从稳定到变化。

| 形态 | 控制方式 | 优点 | 缺点 |
|---|---|---|---|
| LangChain | 程序员硬编码流程 | 稳定、可控、适合工程化 | 灵活性低，改动需要写代码 |
| Workflow | 低代码拖拽流程 | 比代码更容易配置 | 复杂分支会变笨重 |
| Skill | 文档规则加脚本，由 agent 按需执行 | 兼顾灵活性和可控性 | 仍然需要组织目录和说明 |
| 纯 Agent | agent 自主规划和执行 | 最灵活，能临场调整 | 最不可控，可能浪费 token 或把简单事复杂化 |

Skill 的位置比较微妙：它不是最稳定的，也不是最自由的，而是试图在两者之间找平衡。它把可复用经验写进文档和脚本，同时保留 agent 根据自然语言任务做判断的空间。

### 12:20 - 13:04 最底层的方法论：所有技术都在操作上下文和确定性流程

作者最后把这些概念归到更本质的层面：大多数技术最终还是围绕“提示词”和“上下文”转。

Search、RAG、Skill 等，都是在自动把额外内容加入上下文。Agent 则是在减少人和模型之间来回沟通的次数，把可以程序化的部分自动完成。

这里有一个很重要的判断：

- 模糊判断交给模型，例如识别用户到底想做什么。
- 确定流程交给程序，例如读取 PDF、调用 API、保存 Markdown。

所以作者说 agent 是“所有不需要智能的部分构成的部分”。意思不是 agent 没价值，而是它的价值恰恰在于把不需要模型推理的事情固化成程序，把模型只用在语义判断和生成上。

### 13:07 - 14:39 未来趋势：术语会退后，便利性会胜出

作者认为现在 agent 产品最大的限制之一是 token 成本。越强大的 agent，背后自动处理的步骤越多，消耗的 token 也越多。但随着模型推理成本下降，使用便利性会越来越重要。

他类比 Spring Boot 和 uv：很多时候，开发者和普通用户都会优先选择更省心的工具，而不是理论上最节省资源、最精细可控的方案。

对于普通用户来说，未来不应该要求他们理解 MCP 配置、Skill 目录、模型 API Key、workflow 节点。真正有趋势的产品，会把这些都打包好，让用户直接通过自然语言、社交软件、定时任务、可视化管理页面等方式使用。

因此，作者对未来的判断是：

- MCP、Skill、workflow 这些名字本身可能都是阶段性产物。
- 常用工具会被 agent 主程序或基础包内置。
- 普通人最终需要的不是会配置一堆协议，而是一个开箱即用、能调用工具、能管理任务、能长期工作的超级 agent。

## 核心概念速查

| 概念 | 一句话理解 |
|---|---|
| LLM | 会根据上下文继续生成文本的大语言模型 |
| Prompt | 每次发给模型的完整输入 |
| Context | prompt 里的背景、资料、历史、规则等上下文 |
| Memory | 把历史信息重新整理后放回 context，让模型看起来有记忆 |
| Search | 从外部获取模型参数以外的信息 |
| RAG | 从文档或知识库里按语义检索片段，再放入上下文增强生成 |
| Agent | 夹在用户、模型、工具之间的调度程序 |
| Function calling | 模型向 agent 表达工具调用意图的格式约定 |
| MCP | agent 发现和调用外部工具服务的协议 |
| Workflow | 提前设计好的低代码任务流程 |
| LangChain | 用代码串联模型和工具步骤的框架 |
| Skill | 给 agent 读取的说明文档、脚本和资源包 |
| Sub-agent | 用独立上下文处理子任务，减少主上下文污染 |

## 我的理解

这篇视频最值得保留的不是某个术语定义，而是一套拆解 AI 工具的视角：

1. 先问这个东西站在哪一层：用户和 agent 之间、agent 和模型之间，还是 agent 和工具之间。
2. 再问它解决什么问题：补上下文、调工具、固定流程、隔离上下文，还是降低用户配置成本。
3. 最后判断它的代价：更稳定还是更灵活，更可控还是更方便，更省 token 还是更像自然语言产品。

用这个视角看，新名词就不会那么吓人。很多新概念只是把“提示词、上下文、工具调用、脚本、协议、流程控制”重新组合了一遍。真正重要的是：哪些部分应该让模型判断，哪些部分应该写成程序，哪些配置应该被产品隐藏起来。
