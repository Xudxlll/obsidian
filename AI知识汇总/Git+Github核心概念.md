### `00:50` Git 与 GitHub 的关系：版本控制工具与代码托管平台

Git 是一个开源免费的 **版本控制系统**。它解决的是“项目在不断变化时，如何保存历史版本、追踪每次修改、必要时回到旧状态”的问题。

作者用写论文举例：很多人会保存“第一版、第二版、定稿版、最终版”等文件，这其实就是最原始的人工版本控制。Git 把这件事自动化、系统化了，尤其适合包含大量文件、多人协作的大型项目。

当一个文件夹被 Git 管理后，它就变成了一个 **Git 仓库**，里面会出现一个 `.git` 子文件夹，用来保存版本历史和仓库状态。Git 通过一次次 **commit（提交）** 记录项目快照，最终形成一条可回溯的提交历史链。

Git 仓库分为两类：

- **Local Repository，本地仓库**：存在自己电脑上的仓库。
- **Remote Repository，远端仓库**：存在服务器上的仓库，用于备份、共享和协作。

GitHub 则是一个提供远端 Git 仓库托管的网站。它不是 Git 本身，而是建立在 Git 之上的代码托管与协作平台。开发者可以把本地项目上传到 GitHub，也可以浏览、学习、下载、fork 或参与全世界的开源项目。

GitHub 仓库又分为：

- **公开仓库**：所有人都能搜索、浏览和学习代码。
- **私有仓库**：只有拥有权限的人可以查看。

作者还指出，GitHub 只是远端仓库服务之一，类似服务还有 GitLab、Bitbucket 等。理解了 GitHub，迁移到其他平台也会容易很多。

### `03:57` 实战准备：安装 Git、VS Code，注册 GitHub，并让 AI 完成绑定

正式操作前，需要准备以下工具：

1. 安装 Git。
2. 安装 VS Code。
3. 注册并登录 GitHub。
4. 配置至少一个 AI 编程工具，例如 Codex 或 Claude Code。

接着安装 VS Code，并注册 GitHub 账号。登录 GitHub 后，可以新建一个仓库，再把仓库地址交给 Codex，让 AI 帮忙完成本地 Git 项目初始化和推送到 GitHub 的绑定流程。

这里作者的实用建议是：**第一次 Git 与 GitHub 绑定可以直接交给 AI 做**。你只需要告诉 AI：把这个文件夹初始化成 Git 项目，并推送到指定 GitHub 仓库。AI 会在底层完成初始化、授权、远端绑定和推送等操作。

### `06:24` 初始化仓库与 `.gitignore`：哪些内容应该被 Git 管理

`git init` 的意思是初始化仓库。对一个文件夹执行初始化后，这个文件夹就开始被 Git 管理，并生成 `.git` 子文件夹。

如果删除 `.git` 子文件夹，就等于取消 Git 对这个文件夹的管理，它也就不再是一个 Git 仓库。

随后作者讲到 `.gitignore` 文件。它用于声明：哪些文件或文件夹不应该被 Git 管理，也不应该被提交到仓库中。

常见应该忽略的内容包括：

- `.env`：通常保存 API Key、密钥、账号配置等敏感信息，不能上传到 GitHub。
- `node_modules/`：Node.js 项目依赖包目录，文件数量巨大，可以通过 `npm install` 重新生成，不需要提交。
- 构建产物、缓存文件、本地配置文件等。

作者建议：**`.gitignore` 最好在项目初始化时就创建好**，避免一开始就把密钥或无关依赖提交进仓库。

使用 AI 时，可以直接说：

> 把这个目录进行 Git 初始化，注意把不需要提交的内容都排除掉。

AI 通常会自动生成 `.gitignore`，并把 `.env`、`node_modules/` 等常见不应提交的内容排除出去。

### `08:29` Commit 提交：Git 版本历史的基本单位

Commit 是 Git 版本控制的基本单位。每完成一次 commit，Git 就保存一次仓库当前状态的快照。随着 commit 增多，仓库会形成一条完整的历史链路，可以追踪每次改动，也可以在需要时回到历史状态。

在 VS Code 中，可以在 Source Control 面板查看当前改动，填写 commit message，然后点击 commit 完成提交。commit message 应该简短说明这次改动做了什么。

作者给出一个很适合 AI 编程的工作习惯：

> 每让 AI 完成一个小功能点，就做一次 commit。

这样做的好处是：

- 每一步都有历史记录；
- AI 改坏了可以快速撤销；
- 可以清楚比较不同阶段的变化；
- 后续让 AI 按 commit id 回退或分析会更精确。

每个 commit 都有唯一的 **commit id / commit hash**。它有长 id 和短 id 两种形式，短 id 通常就是长 id 的前几位。在和 AI 沟通时，最好直接给 commit id，而不是只说“刚才那次提交”，这样更准确。

这一段还讲了几种常见“后悔药”：

#### 1. Discard：撤销还没提交的改动

当文件已经被修改，但还没有 commit 时，可以使用 discard changes 放弃当前改动，让文件回到上一次提交后的状态。

适合场景：AI 刚改完但结果明显不对，还没有提交，可以直接丢弃这次改动。

#### 2. Reset：强制回到某个历史提交

Reset 会把仓库强制回退到某个历史状态。它可以删除某个提交之后的历史。

适合场景：单人分支上，或者错误提交还没有推送到远端时。

风险：如果这些提交已经推送到远端，再 reset 往往需要强制推送，可能覆盖别人代码，所以多人协作分支上不应随便使用。

#### 3. Revert：用反向提交抵消某次提交

Revert 不会删除历史，而是生成一个新的反向提交，用来抵消某次错误提交。

适合场景：多人协作分支、已经推送到远端的提交、需要保留完整历史的场景。

结论：**多人协作中优先用 revert，单人未推送场景才考虑 reset。**

作者还演示了用 AI 比较两个 commit 的区别。底层可能是 `git diff`，但用户只需要理解“比较两个提交之间发生了什么变化”，再把两个 commit id 交给 AI 即可。

### `14:18` Branch 分支：在不影响主干的情况下开发新功能

Branch 是仓库中的不同开发线。每个仓库通常有一个 `main` 或 `master` 主干分支。创建分支相当于从某个提交点拉出一条新的开发线。

分支的关键作用是：**隔离改动**。

例如，从 `main` 创建一个 `feature` 分支后，刚开始两个分支内容相同。但你在 `feature` 上提交的新改动，只会出现在 `feature` 分支，不会影响 `main`。等功能完成后，再把 `feature` 合并回 `main`，这个过程叫 **merge（合并）**。

分支对多人协作和多 AI Agent 协作非常重要：

- 每个人可以在自己的分支上开发；
- 每个 AI Agent 可以在独立分支上尝试方案；
- 主干分支保持稳定；
- 功能完成后再合并。

作者还强调：分支在 Git 底层主要是通过指针实现的，并不是复制一整份代码，所以创建分支很轻量。

#### 基于历史提交创建分支

除了从主干最新状态创建分支，也可以从任意历史 commit 创建分支。这样可以安全地回到某个历史状态继续开发。

这里作者对比了两种回到历史的方式：

- **Checkout detached / 分离头指针**：适合查看历史版本，不适合修改代码，容易搞丢改动。
- **基于历史 commit 创建新分支**：适合从旧版本继续开发，因为有分支管理，更安全。

#### HEAD 的含义

HEAD 表示当前仓库正处在哪一次 commit 上。通常 HEAD 指向当前分支的最新提交；如果 checkout 到某个历史提交而不在任何分支上，就会进入 detached HEAD 状态。

理解 HEAD，有助于理解“我现在到底在哪条分支、哪个提交点上工作”。

### `17:50` Worktree：让多个分支拥有独立文件夹，并行开发

Worktree 可以理解为：基于 Git 创建一个新的分支，并把这个分支的工作区放到一个新的文件夹里。

普通分支切换是在同一个文件夹里来回切换代码；Worktree 则是让不同分支各自拥有独立文件夹。因此可以同时打开多个目录，并行开发、测试、运行，不互相干扰。

这对 AI 编程特别有用：

- 一个主目录保持稳定；
- 多个 worktree 分别交给不同 AI 处理不同任务；
- 各自完成后再合并回主干；
- 可以提高并行开发效率。

Codex App 中可以直接创建永久工作树；Claude Code 也可以通过 worktree 命令启动到新目录中。

#### Merge conflict 合并冲突

当两个分支修改了同一个文件的同一行，Git 无法自动判断应该保留哪个版本，就会产生 **merge conflict（合并冲突）**。

过去解决冲突比较繁琐，现在可以让 AI 辅助处理。作者演示了让 Codex 合并两个分支，遇到冲突时暂停并询问用户。用户可以选择：

- 保留左边版本；
- 保留右边版本；
- 两个都保留；
- 按指定顺序合并内容。

关键点是：AI 可以帮你执行冲突解决，但最终应该保留什么内容，仍然需要用户根据业务逻辑决定。

### `20:52` Git 分区：工作区、本地仓库、远端仓库与暂存区

作者把 Git 的工作流拆成几个区域来理解。

#### 1. Working Directory，工作区

工作区就是你电脑磁盘上的项目文件夹。你平时编辑、创建、删除文件，都是在工作区发生的。

#### 2. Staging Area / Index，暂存区

暂存区是 commit 前的检查点。你可以选择哪些文件进入暂存区，下一次 commit 只提交暂存区里的内容。

在命令行中通常是先 `git add`，再 `git commit`。不过很多图形化工具会弱化这个概念，例如 VS Code 可以点击一次 commit 按钮就自动完成 add + commit。

暂存区的价值在于：当你一次修改了很多文件，但只想把其中一部分作为一次提交时，可以只 stage 需要提交的文件。

#### 3. Local Repository，本地仓库

commit 之后，改动会进入本地仓库。此时这些提交只保存在你的电脑上，别人还看不到。

#### 4. Remote Repository，远端仓库

远端仓库通常指 GitHub 上的仓库，也可以是 GitLab、Bitbucket 或自建服务器。远端仓库用于备份、共享和多人协作。

#### 常见同步动作

- `clone`：把远端仓库复制到本地，同时得到本地仓库和工作区。
- `add + commit`：把工作区改动提交到本地仓库。
- `push`：把本地仓库的提交推送到远端仓库。
- `pull`：把远端仓库的最新提交拉到本地并合并。
- `fetch + merge`：先获取远端变化，再手动合并；`pull` 可以理解为这两步的组合。

这一部分的核心是：**Git 的大多数操作，本质上都是在这些区域之间同步代码。**

### `23:26` 远端仓库实战：clone、push、pull 与本地远端同步

本地仓库和远端仓库建立关系，主要有两种路径。

#### 路径一：先有远端仓库，再 clone 到本地

可以先在 GitHub 创建一个仓库，选择公开或私有，也可以初始化 README、`.gitignore` 和许可证。创建后复制仓库地址，在 VS Code 中使用 clone，把远端仓库下载到本地。

之后的流程是：

1. 在本地修改代码；
2. commit 到本地仓库；
3. push / publish 到 GitHub；
4. 在 GitHub 页面刷新后看到本地提交。

注意：只有仓库管理员或被授予权限的人才能 push 到该仓库。普通用户不能直接向别人的仓库 push 代码。

#### 路径二：先有本地文件夹，再推送到 GitHub

如果本地已经有一个项目文件夹，但还不是 Git 仓库，可以先在 VS Code 里 init，再 commit，最后点击 publish，选择创建公开或私有远端仓库。

这种方式适合：本地已经写了一些代码，现在想把它纳入 Git 管理并上传到 GitHub。

#### 拉取远端改动

如果你或协作者在 GitHub 远端直接修改了代码，本地暂时看不到。此时需要 pull / sync changes，把远端提交拉取到本地。

有远端后，通常会看到两类分支状态：

- `main`：本地分支；
- `origin/main`：远端分支在本地的追踪记录。

当本地比远端多提交时，需要 push；当远端比本地多提交时，需要 pull。同步完成后，本地和远端会指向同一个提交状态。

### `27:33` GitHub 入门：如何阅读一个开源项目

GitHub 仓库地址通常由三部分组成：

```text
https://github.com/开发者名/仓库名
```

进入仓库后，中间最显眼的是代码区，里面存放项目源代码。每个文件旁边会显示最近一次 commit message 和更新时间。如果项目文件多年没有更新，通常说明它可能已经缺乏维护。

#### README

代码区下方通常会显示 README 内容。README 是项目说明书，通常介绍：

- 这个项目是什么；
- 解决什么问题；
- 如何安装；
- 如何运行；
- 如何参与贡献。

#### Releases

Releases 区域记录项目发布版本。Assets 中通常会有打包好的软件或可下载文件。普通用户如果只是想使用软件，往往可以直接从 Releases 下载，而不一定需要自己编译源码。

#### About、Star、Fork

右侧 About 区域展示项目简介、标签、Stars、开源协议等。

- **Star** 类似点赞加收藏，可以反映项目热度。
- **Fork** 是把别人的项目复制一份到自己名下，方便学习、修改和提交贡献。

#### Issues

Issues 是项目讨论区。用户可以在这里提交 bug、提出新功能建议、参与讨论或搜索已有解决方案。

Issues 通常分为：

- Open：还未解决或仍在讨论；
- Closed：已经解决或讨论结束。

在使用开源项目遇到问题时，先搜索 Issues 往往能找到别人已经踩过的坑和解决方案。

#### GitHub 常用快捷键

作者介绍了几个实用快捷键：

- `/`：快速打开 GitHub 搜索。
- `T`：在当前仓库中快速搜索文件。
- `L`：快速跳转到某一行代码。
- `?`：打开快捷键速查表。
- `.`：打开 GitHub 网页版 VS Code，用浏览器像 VS Code 一样查看项目。

还可以通过 GitHub Codespaces 申请云端开发环境，在浏览器里运行、调试和修改代码。

### `32:29` GitHub 多人协作：Fork、分支、Pull Request 与 Code Review

这一段讲的是如何给别人的开源项目贡献代码。

普通用户通常没有权限直接 push 到别人的仓库，所以标准流程是：

1. 在 GitHub 上 fork 原项目，把它复制到自己账号下。
2. clone 自己 fork 出来的仓库到本地。
3. 在本地创建 feature 分支，不要直接改 main。
4. 在 feature 分支上修改代码并 commit。
5. push 自己的 feature 分支到自己的 GitHub 仓库。
6. 创建 Pull Request，请求把自己的分支合并进上游项目。
7. 上游项目管理员进行 Code Review。
8. 审核通过后，管理员 merge，代码进入主项目。

作者更喜欢把 Pull Request 翻译成“合并请求”，因为它本质上就是：请求把一个分支的改动合并到另一个分支。

#### 提 PR 前要先同步上游最新代码

如果你 fork 之后，上游项目又新增了提交，而你的 feature 分支也做了修改，那么直接提 PR 可能产生冲突。

正确做法是：

1. 先把上游项目的最新改动同步到自己的 feature 分支；
2. 如果有冲突，先在本地解决；
3. 再把解决后的结果 push 到自己的仓库；
4. 最后创建 PR。

这一步可以交给 AI 做，例如告诉 Codex：

> 这是上游项目地址，请把上游项目的最新改动合并进当前 feature 分支；如果有冲突，先停下来让我选择怎么处理。

#### Collaborator 协作者模式

如果是公司内部项目，或者仓库管理员把你添加为 collaborator，你就不需要 fork 了。你可以直接 clone 原仓库、创建分支、push 分支，再提交 PR 给管理员审核。

这和开源贡献的主要区别是：

- 开源外部贡献者：通常先 fork。
- 仓库协作者：可以直接在原仓库拉分支并 push。

但无论哪种方式，都建议：**不要直接在 main 上改代码，而是通过分支 + PR + Code Review 的流程协作。**

### `38:21` 进阶操作：Cherry-pick、Stash、Rebase

视频最后补充了几个 Git 进阶概念。

#### Cherry-pick：只挑选某几个提交合并

Cherry-pick 字面意思是“挑樱桃”，在 Git 中表示“拣选提交”。

例如 feature 分支上有三个 commit：蔬菜清单、肉类清单、主食清单。如果只想把“蔬菜清单”和“主食清单”合并进 main，而不合并“肉类清单”，就可以 cherry-pick 指定的 commit id。

适合场景：一个分支里有多个提交，但只想拿其中几个特定改动。

#### Stash：临时保存未完成的工作

Stash 是临时存储，和 staging area 暂存区不是一回事。

典型场景是：你正在 feature 分支写代码，代码写到一半还不能 commit，但突然需要切到 main 分支处理紧急任务。如果直接切换，未完成的改动可能会跟着带过去，造成混乱。

此时可以：

1. 把当前未完成改动 stash 起来；
2. 切换到 main 处理紧急任务；
3. 回到 feature 分支；
4. 用 pop 把刚才 stash 的改动取回来继续写。

Stash 适合临时中断工作，但如果一个改动已经形成清晰阶段，作者更建议直接 commit。

#### Rebase：变基，让提交历史更干净

Rebase 可以理解为把当前分支的“根基”移动到另一个分支的最新位置上。

从效果上看，它也能实现“把 main 的最新改动合并进 feature”。但和普通 merge 不同，rebase 不会生成额外的 merge commit，提交历史会更像一条直线，因此更干净。

作者给出的重要提醒是：

- Rebase 会改写提交历史；
- Rebase 后通常需要强制推送；
- 强制推送可能覆盖别人代码；
- 所以 rebase 和 force push 只适合自己单独使用的分支；
- 多人共同使用的分支不要随便 rebase + force push。

## 核心速记

- **Git**：本地版本控制工具，负责记录项目历史。
- **GitHub**：远端代码托管与协作平台。
- **`.git`**：保存仓库版本信息的隐藏目录。
- **`.gitignore`**：声明哪些文件不纳入 Git 管理。
- **Commit**：一次项目快照，是版本历史的基本单位。
- **Commit id**：提交的唯一标识，和 AI 沟通时非常有用。
- **Discard**：撤销未提交改动。
- **Reset**：强制回到历史状态，慎用于已推送或多人协作分支。
- **Revert**：生成反向提交，更适合多人协作。
- **Branch**：独立开发线，用于隔离功能开发。
- **HEAD**：当前仓库所在的提交位置。
- **Worktree**：给不同分支创建独立文件夹，适合多任务并行。
- **Staging Area**：commit 前的暂存检查点。
- **Push**：把本地提交推到远端。
- **Pull**：把远端提交拉回本地并合并。
- **Fork**：把别人的仓库复制到自己账号下。
- **Pull Request**：请求把一个分支的改动合并到另一个分支。
- **Code Review**：管理员或协作者审核 PR 代码。
- **Cherry-pick**：只挑选指定 commit 合并。
- **Stash**：临时保存未完成改动。
- **Rebase**：变基，能整理历史，但会改写提交历史，需谨慎使用。

## 对 AI 编程最重要的实践建议

1. **不要只让 AI 直接改代码，要让它配合 Git 工作。**
2. **每完成一个小功能就 commit 一次。**
3. **给 AI 指令时尽量使用 commit id、分支名、文件名等明确对象。**
4. **AI 改错且还没 commit 时，用 discard。**
5. **本地单人分支想整体回退，可考虑 reset。**
6. **多人协作或已经推送的提交，优先使用 revert。**
7. **新功能、新实验、新 Agent 任务都应该开分支或 worktree。**
8. **合并前先同步主干最新代码，有冲突先本地解决。**
9. **向开源项目贡献代码时，走 fork → branch → commit → PR → review → merge 流程。**
10. **rebase 和强制推送只在自己独立分支上谨慎使用，避免覆盖别人代码。**
